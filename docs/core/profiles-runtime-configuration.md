# Profiles and Runtime Configuration

## Profile Sources

Kumo models profiles with `ProfileSource`:

- `remote(URL)` for subscription URLs.
- `file(URL)` for local Clash or Mihomo YAML files.
- `inline` for generated fallback profiles.

Kumo supports local files, remote refresh, and profiles generated by the bundled
Sub-Store backend. In
that case profile metadata records the original Sub-Store download path and
refresh rebuilds the request against the current local backend URL with
`target=ClashMeta` and `noCache=true`.

## Subscription Normalization

Every import and remote refresh is normalized before it can become current.
Kumo accepts either a Mihomo YAML mapping or a plain/Base64-encoded list of node
URIs. Scalar YAML, HTML error pages, empty responses, oversized documents, and
converted documents without usable proxy nodes are rejected without changing
the selected profile.

Raw node subscriptions are converted to `ClashMeta` YAML by an isolated launch
of the bundled Sub-Store parser. The converter binds only to a random loopback
port, uses a private temporary data directory, disables scheduled jobs, and is
terminated after the request. Shutdown is bounded: Kumo requests termination,
polls for at most one second, escalates to `SIGKILL`, and polls only briefly
again. It never performs an unbounded `Process.waitUntilExit()`, so a vanished
Node child cannot leave subscription import spinning forever. If conversion
returns proxies but no group or rules, Kumo adds a `Kumo Subscription` select
group and a matching fallback rule. This supports, among other formats handled
by Sub-Store, VLESS and Hysteria2 links inside standard or URL-safe Base64
subscriptions.

Conversion always happens in the desktop app or CLI process. Before a request
is sent to Kumo Helper, the normalized YAML is persisted with user-only file
permissions. The privileged Helper does not launch the bundled parser and only
accepts an already normalized Mihomo YAML mapping. This keeps legacy migration
compatible without making the Helper depend on a SwiftPM resource bundle.

## Default Profile

If no default profile exists, `ProfileRepository` returns a minimal direct profile:

```yaml
proxies: []
proxy-groups:
  - name: Proxy
    type: select
    proxies:
      - DIRECT
rules:
  - MATCH,DIRECT
```

This lets the app start with a safe empty state instead of crashing on missing configuration.

## Transactional Activation

Importing a profile first stores it as non-current. Selection changes, edits,
refreshes, Sub-Store imports, deletes, and scheduled refreshes then pass through
one serialized activation coordinator. The coordinator first normalizes the
document and builds its candidate runtime configuration without touching the
live core. What happens next depends on the observed run state and activation
policy:

- If the runtime is running, ambiguous, or the policy requires a start, Kumo
  runs bounded Mihomo `-t` validation before stopping the previous generation,
  starts or restarts the candidate, and verifies PID/start-time identity, the
  controller and mixed listeners, an exact activation receipt, and `/proxies`.
  The receipt must match the candidate's profile ID, new runtime generation,
  and final configuration SHA-256. Only that verified generation may commit
  `current.txt`.
- If the runtime is strictly stopped and the policy preserves that stopped
  state, Kumo performs normalization plus `RuntimeConfigBuilder` structural
  validation, commits the selection, and leaves Mihomo stopped. This path does
  not claim Mihomo `-t` or live-controller verification; the first later start
  performs the semantic and readiness checks before exposing live data.

If candidate activation fails, Kumo restores both the previous profile content
and its previous running/stopped state. Deleting the current profile activates a
verified fallback before removing its files. Scheduled refresh restores every
profile already changed by a partially failed batch. A legacy raw Base64 profile
is normalized by the App or CLI on its next activation before the Helper is
contacted.

Before the first process mutation, Kumo freezes both the candidate and rollback
inputs as immutable `RuntimeSpec` values. Each spec contains the normalized
profile YAML, exactly the applicable ordered overrides, controlled runtime
settings, and the SHA-256 of the fully generated YAML. The Helper regenerates
the YAML from that spec and rejects it if the digest differs. Rollback therefore
restarts the captured previous configuration rather than rereading files that
may have changed during the failed transaction. Rollback first re-observes
Helper state: when candidate cleanup left either `.stopped` or `.failed` with
no PID, readiness, or generation, it starts the previous spec with a stopped
generation expectation; otherwise it restarts against the exact live generation.

## Runtime Config Generation

`RuntimeConfigBuilder` appends Kumo-controlled runtime settings to the selected profile:

- `external-controller`
- `secret`
- `mixed-port`
- `mode`
- `allow-lan`
- `log-level`
- `ipv6`
- `find-process-mode`
- Geo data settings
- TUN settings when Kumo TUN is enabled
- DNS settings when Kumo DNS is enabled
- Sniffer settings when Kumo Sniffer is enabled
- `hosts` when the user has configured hosts in the Kumo UI

The goal is to keep user profiles portable while ensuring Kumo can control the running core.
In privileged Helper mode, `tun`, `dns`, `hosts`, `sniffer`, and custom
`listeners` are always removed from profile and override input. Only typed
runtime settings carried by the signed request may recreate those blocks.
Kumo sets `find-process-mode: always` by default so the Mihomo controller
returns `processPath` metadata for active connections; the macOS Connections
view uses that path to display native application icons.

HTTP `proxy-providers` and `rule-providers` receive Kumo-owned cache paths in
both local and Helper runtime builds. The path contains a SHA-256 namespace for
the profile ID followed by a SHA-256 identity derived from the provider key and
URL, for example `./providers/proxy/<profile-hash>/<provider-hash>.yaml`.
Identical inputs remain stable, while switching profiles or changing either the
provider key or URL selects a different cache and cannot reuse stale provider
content from the previous profile.

Profile kind does not change the activation contract. Native YAML, normalized
plain/Base64 node subscriptions, and YAML containing HTTP proxy/rule providers
all produce an immutable spec and must obtain a new matching generation and
configuration digest before their nodes can be shown as active. This prevents a
successful metadata selection from leaving traffic on the prior subscription.

## Overrides

Kumo applies an ordered override layer:

1. Selected profile YAML.
2. Profile-specific overrides.
3. Global overrides.
4. Kumo-controlled runtime settings.

The final layer always wins for controller address, ports, mode, and other
Kumo-owned keys. Kumo removes profile-provided HTTP, SOCKS, redir, and tproxy
listener ports and exposes the configured local proxy surface through its
controlled `mixed-port`.
When Kumo TUN, DNS, or Sniffer is enabled, the final layer owns the respective
top-level blocks (`tun`, `dns`, `sniffer`) so UI settings are reflected in the
generated runtime configuration. In Helper mode these blocks, `hosts`, and
custom `listeners` remain owned by Kumo even while disabled.

Every non-global override created or edited through `KumoController` is bound
to the profile selected by that transaction. Legacy non-global metadata that
does not contain a profile ID remains readable for migration and editing, but
is never applied to any runtime. Creating a profile-scoped override, editing a
legacy unscoped item, or changing a global item to local binds it to the current
profile; callers cannot provide a different profile ID. An existing scoped item
can be edited, deleted, or reordered only while its owning profile is selected.
Runtime generation always asks the repository for overrides matching the target
profile ID, so switching profiles cannot carry nodes or rules from the
previously selected subscription.

Override add, remote import, edit, delete, and reorder operations share the
profile operation gate and its cross-process file lock. Kumo snapshots the
complete override repository before mutation. A profile-scoped change
structurally preflights the selected profile. Because a global override affects
every profile, global add/edit/delete/reorder structurally preflights every
stored profile with `RuntimeConfigBuilder`; this is deliberately described as
structural preflight, not as Mihomo `-t` validation of every dormant profile.
When Mihomo is live, Kumo semantically validates, restarts, and verifies the
selected profile generation. A failed preflight restores the files without
touching the live runtime; a failed activation restores both the snapshot and
the previously verified runtime.

## Current Merge Strategy

The current implementation parses YAML into structured values before merging:

1. The selected profile provides the base document.
2. Later overrides recursively merge mapping values.
3. Array and scalar values replace earlier values by default.
4. Explicit sequence operators can prepend, append, or delete array entries.
5. Kumo-owned runtime keys are removed from user-provided documents.
6. Kumo-controlled runtime settings are appended last and always win.

Kumo supports Sparkle-style sequence operators (`+rules`, `rules+`, and the
same shape for other array keys) and Clash Verge Rev-style rule operators
(`prepend-rules`, `append-rules`, `delete-rules`). These operator keys are
consumed during generation and are not written to the final runtime
configuration. A key ending in `!` replaces the target value directly instead
of recursively merging nested mappings.

This gives deterministic precedence for common Mihomo configuration sections
without introducing JavaScript transforms or a privileged service dependency.
Full YAML comments and formatting are not preserved because the generated
runtime file is serialized from structured values.

TUN advanced setting edits are persisted to `CoreRuntimeSettings.tun`. Applying
them while Mihomo is running restarts the core, matching Mihomo's expectation
that interface-level TUN changes are loaded from the generated runtime YAML
rather than patched piecemeal.
